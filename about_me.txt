What makes the documents hard:
- Dense regulatory content (IEC 62304, FDA, CE marking references) with non-standard structure
- Multi-format sources: PDFs with embedded tables, images, numbered requirements, cross-references
- Domain-specific medical device terminology outside standard LLM vocabulary
- Documents too long for single-context retrieval; cross-document reasoning required

What was built:
- Custom preprocessing pipeline: domain-aware chunking (respects section boundaries and
  numbered requirements), metadata extraction (document type, version, regulation reference),
  semantic deduplication to eliminate near-duplicate spec sections that confuse retrieval.
- Tiered retrieval architecture: BM25 lexical pre-filter (eliminates ~90% of irrelevant chunks,
  near-zero cost) → dense embedding reranker (cross-encoder, scores top-K candidates) → LLM
  generation with cited sources. Each tier's threshold tuned for precision/recall trade-off.
- Cost optimization: Anthropic prompt caching (cache_control on system prompt + base context)
  reduces API costs by ~80% on repeated queries. Minimal-context generation — only retrieved
  passages, not the full corpus, passed to the LLM.
- Query decomposition: complex multi-part questions are decomposed into sub-queries by a
  lighter LLM before retrieval, then answers are synthesized. Handles "what are the FDA
  requirements for X and how do they interact with Y?" type queries.
- MCP integrations: RAG system connected via MCP servers to JAMA (requirements management),
  Confluence (internal wikis), and engineering docs — unified natural language interface across
  all sources.
- Claude Code skills orchestration: each pipeline stage (ingest, chunk, embed, retrieve,
  generate, evaluate) is an autonomous skill. Same architecture as the StationF outreach agent.
- SDLC automation agents (parallel): code review agent (reviews PRs, flags regressions),
  documentation generator (auto-generates from code), test generation agent.

Impact: replaced hours of manual expert document lookup with a seconds-latency NL query

3. LEROBOT — Robotics RL & MLOps Pipeline
   Built a complete MLOps pipeline for training autonomous robotic manipulation agents using
   Diffusion Models and the ACT (Action Chunking Transformer) architecture.

   The task: PushT — a robotic arm must push a T-shaped block to a precise target position and
   orientation on a 2D surface. Simple to describe, hard to solve: the block dynamics are
   non-linear, orientation matters, and small trajectory errors compound.

   What was built:
   - Training pipeline: demonstration data collection → dataset preprocessing → ACT model
     training with behavioral cloning → policy evaluation loop. All reproducible via config.
   - Model architecture: ACT predicts a chunk of future actions (not just the next action)
     which smooths trajectories and reduces the compounding error problem.
   - MLOps: experiment tracking, model versioning, checkpoint management, training resumption.
   - Deployment: trained model and an interactive training UI published on Hugging Face,
     allowing anyone to retrain or evaluate the policy without local GPU.

   Stack: Python, PyTorch, Hugging Face Hub, LeRobot framework, Google Colab (training).
   Model: https://huggingface.co/zino36/lerobot-pusht-colab
   Training UI: https://huggingface.co/spaces/zino36/lerobot-pusht-trainer

4. MEDICAL LUNG CANCER CLASSIFICATION (CT Scan Deep Learning)
   Deep learning pipeline for automated lung cancer detection and classification from
   grayscale CT scan images — a medical imaging problem with specific challenges:
   - CT scans are grayscale, not RGB: most standard CNNs assume 3-channel input;
     the pipeline was adapted for single-channel grayscale input.
   - Medical images have extreme class imbalance (far fewer cancerous samples).
   - Clinical metrics matter beyond accuracy: sensitivity (recall on cancer class) and
     specificity are the meaningful measures, not overall accuracy.

   Built and compared two architectures on the same dataset:
   - CnnGrayscaleModel: convolutional layers with max-pooling, batch normalization,
     dropout regularization. Better at spatial feature extraction.
   - MlpGrayscaleModel: fully-connected layers on flattened grayscale input. Simpler
     baseline that shows the gain from convolutional inductive bias.
   Full pipeline: DICOM/image loading, grayscale preprocessing and normalization,
   data augmentation (flips, rotations), training, confusion matrix, per-class metrics.

   Stack: Python, PyTorch/TensorFlow, medical imaging libraries (pydicom/OpenCV).
   GitHub: https://github.com/ZinebMEFTAH/medical-lung-cancer-classification

5. NLP SEMANTIC CLUSTERING — Amazon Reviews
   Research comparison of traditional vs. modern NLP approaches for unsupervised text clustering.

   The question: can neural sentence embeddings produce meaningfully better clusters than
   classic bag-of-words on real-world review text?

   Two approaches on the same Amazon review dataset:
   - Bag-of-Words (BoW): TF-IDF weighted term-frequency vectors. Fast, interpretable,
     but treats "good" and "excellent" as completely unrelated.
   - Sentence Transformers (thenlper/gte-small): dense neural embeddings that capture
     semantic similarity — "good" and "excellent" land near each other in embedding space.

   Both fed into K-Means clustering. Dimensionality reduced to 2D via PCA for visualization.
   Quality evaluated with Purity Score against ground-truth sentiment labels.
   Result: Sentence Transformer embeddings produce significantly tighter, more coherent clusters.
   The experiment quantifies the gain from semantic understanding vs. syntactic frequency.

   Stack: Python, Scikit-learn, Sentence-Transformers (HuggingFace), Pandas, Matplotlib.
   GitHub: https://github.com/ZinebMEFTAH/nlp-clustering-reviews

6. REINFORCEMENT LEARNING — Q-Learning from Scratch on Gymnasium
   Implemented the Q-Learning algorithm from scratch (no RL libraries) and trained agents
   on three environments of increasing difficulty:

   - FrozenLake 4×4 and 8×8: navigate a stochastic grid (the ice is slippery — actions
     don't always go where intended). Tabular Q-table, epsilon-greedy exploration,
     learning rate decay. Tests sample-efficient exploration under uncertainty.
   - Taxi-v3: a taxi must pick up a passenger and drop them at a target. Sparse reward,
     large discrete state space (500 states). Tests credit assignment over long episodes.
   - CartPole: a pole balanced on a cart. The observation space is continuous (4 floats:
     position, velocity, angle, angular velocity) — tabular Q-learning can't apply directly.
     Solution: state discretization (binning continuous values into discrete buckets),
     which bridges the gap between tabular and deep RL approaches.

   Each agent trained with: epsilon-greedy decay schedule, Q-value convergence monitoring,
   and policy visualizations. Models serialized with Pickle for reuse.

   Stack: Python, Gymnasium (OpenAI), NumPy, Pickle, Matplotlib.
   GitHub: https://github.com/ZinebMEFTAH/rl-qlearning-gymnasium

9. MONCOMPILATEUR — Full Pascal → x86-64 Assembly Compiler
   One-pass recursive-descent compiler translating a Pascal-like imperative language into
   raw x86-64 AT&T assembly. No intermediate representation. No external runtime beyond libc.

   What "one-pass" means and why it's hard: code is emitted as the source is parsed, without
   the ability to look ahead or revise. Every design decision — type resolution, jump targets,
   FPU register management — must be resolved at parse time.

   Full language support implemented:
   - 5 types: INTEGER (unsigned 32-bit), DOUBLE (IEEE-754 64-bit), BOOLEAN (1-byte,
     0x00/0xFF), CHAR (1-byte ASCII), STRING (heap-allocated, null-terminated pointer)
   - Automatic type promotion: integer ↔ double expressions handled transparently.
     Implementation uses x87 FPU with fldl/faddp/fmulp/fdivp/fucomip/fstpl instructions —
     the legacy but precise x87 floating-point unit most students never touch.
   - cvtsi2sd for integer→double promotion in mixed-type expressions
   - All control structures: IF/THEN/ELSE, WHILE/DO, REPEAT/UNTIL, FOR/STEP, CASE/OF
   - Procedures: proper stack frame management (push %rbp; mov %rsp, %rbp), sub $8/%rsp
     for 16-byte alignment before call, leave/ret epilogue
   - String concatenation: a __concatStrings runtime helper, string literals in .rodata
   - Static type checker: symbol table (std::map<string, TYPE>) validates types at
     compile time with descriptive error messages
   - DISPLAY statement: handles all 5 types via printf@PLT with appropriate format strings

   Tested on a 150-line test.p file exercising all features: nested procedures (DeepNested
   calls BuildMessageExtended), mixed integer/double arithmetic, all control structures
   combined, string concatenation chains, boolean and char display.

   Stack: C++17, Flex (lexer), Bison (tokenizer), AT&T x86-64 Assembly, GNU/Linux (System V ABI).
   GitHub: https://github.com/ZinebMEFTAH/MonCompilateur

12. SEARCH ENGINE — TF-IDF & BM25 from Scratch
    Full information retrieval engine built in Java without any IR libraries.

    Pipeline:
    - Preprocessing: lowercase normalization → Porter stemmer (reduces "running", "ran",
      "runs" to "run") → stop word filtering (from stopList.txt) → inverted index construction
    - TF-IDF scoring: term frequency normalized by document length, IDF log-dampened
    - BM25 scoring: industry-standard (used by Elasticsearch/Lucene) with tunable parameters:
      k1 controls term saturation (how quickly additional occurrences stop adding score),
      b controls document length normalization (0 = no normalization, 1 = full normalization)
    - Query processing: tokenize, preprocess, score all candidate documents, rank by score
    - Custom exception hierarchy: CorpusException, TfIdfException, Bm25Exception with
      descriptive messages and class hierarchy visualization

    Tested on WIKIPEDIA.txt and BOOK.txt corpora. BM25 consistently outperforms TF-IDF
    on longer documents due to length normalization.
    Modular architecture: Model layer (Document, Word, Vocabulary) / Engine layer
    (Corpus, TfIdf, Bm25) / Exceptions layer.

    Stack: Java, OOP, Porter Stemmer (Snowball), custom data structures.
    GitHub: https://github.com/ZinebMEFTAH/Search-Engine
